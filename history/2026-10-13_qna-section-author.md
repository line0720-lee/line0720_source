# 문서 관리: 섹션 수정·삭제, 섹션 99개 지원, 등록자 칸 추가

## 상태: 완료 (운영 서버 반영은 차후작업 — 아래 참고)

## 작업 목표
전산도우미(IT_Error) 문서 관리 화면에서
1. 섹션 이름 수정·삭제
2. 섹션 99개까지 추가
3. Q&A 등록·수정 시 등록자 이름 입력(필수)

## 사전 조사
- 섹션 머리글에 버튼이 없었고, 항목이 없는 섹션은 화면에 그리지 않았음
- 로마 숫자가 Ⅰ~Ⅹ 10개뿐이라 11번째부터 `11.`이 붙었는데, 운영 서버 파서는 첫 글자가 Ⅰ~Ⅹ일 때만 섹션으로 인식
  (`/api/parse-docx`로 시험: `ⅩⅠ.` 인식 / `ⅬⅠ.`·`11.` 무시 → 앞 섹션에 합쳐짐)
- 운영 서버는 `[BY:이름]` 줄을 답변 줄로 그대로 보존 → 서버 수정 없이 등록자 저장 가능
- 운영 서버 backend.py는 이 저장소에 없음(9/16 운영 이관 버전, 별도 관리)

## 수행 내용
`IT_Error/index.html`
- `toRoman(n)`: 1~10은 기존 단일 문자, 11~99는 조합(ⅩⅠ, ⅩⅬ, Ⅼ, ⅩⅭⅨ)
- `nextSectionPrefix()`: 안 쓰는 번호를 골라 새 섹션 번호 부여(빈 섹션은 저장되지 않아 번호 빈칸이 생길 수 있음), 99개 제한
- `openEditor`: 섹션 목록을 하드코딩 기본값 대신 문서 항목 순서로 구성
- `renderEditor`: 섹션 머리글에 ✏️ 수정 / 🗑️ 삭제, 빈 섹션은 "항목 없음" 표시
- 섹션 수정: 번호 유지, 이름만 변경(소속 항목도 같이 갱신). 삭제: 항목이 있으면 차단, 비어 있으면 삭제 후 번호 재부여
- 등록자: 추가·수정 폼에 필수 입력칸, `[BY:이름]` 마커로 저장·복원, 카드에 "등록자: 이름" 표시
- 챗봇 청크에서 `[BY:]` 줄 제거(등록자 이름이 검색·답변에 섞이지 않게)
- 저장 시 섹션 순서대로 항목을 묶어 전송(새 항목이 섹션을 둘로 쪼개지 않게)

`IT_Error/backend.py` (로컬)
- 섹션 인식 정규식에 `Ⅼ`, `Ⅽ` 추가
- `save_qna`의 고정 목록 정렬 제거 → 받은 순서대로 저장

### 추가 요청: 섹션 추가 화면에서 수정·삭제
- 툴바 "📁 새 섹션" → "📁 섹션 관리"로 바꾸고, 열리는 패널을 섹션 관리 화면으로 변경
  - 위: 새 섹션 추가(Enter로도 추가), 패널은 추가 후에도 열린 채 유지
  - 아래: 등록된 섹션 목록(번호·이름·항목 수) + 줄마다 ✏️ 수정 / 🗑️ 삭제, 수정은 그 줄에서 바로 입력
- 수정·삭제 규칙은 목록 머리글 버튼과 같은 함수(`renameSectionAt`, `deleteSection`) 사용
- 확인: 추가 → 수정 → 빈 섹션 삭제 → 항목 있는 섹션 삭제 차단 → 이름 변경 시 항목 3개 함께 이동 (운영 데이터로 화면만 조작, 저장 안 함)

### 추가 요청: 섹션 제목 옆 버튼 제거, 번호 01~99 표시, 아이콘 새로고침
- 섹션 제목 옆 수정·삭제 버튼 제거(섹션 관리 패널에서만 수정·삭제), 관련 함수 정리
- 번호 표시: 문서에는 로마 숫자로 저장(서버 파서 호환), 화면에만 01~99로 표시(`displayNum`, `displaySection`)
  - 섹션 제목, 패널, 섹션 선택 목록, 챗봇 참고 구간·답변 근거에 적용
- 헤더 🏥 아이콘 클릭 시 `location.reload()`

### 추가 요청: 섹션 관리 변경 즉시 저장
- `postQnaSave()`로 저장 요청 공통화, `saveSectionChange()`가 이름 수정·삭제 직후 서버 문서에 바로 저장
  - 연속 변경 시 요청이 겹치지 않게 하나씩 처리, 마지막 상태가 저장됨
  - 401이면 "저장 권한이 없습니다 (로그인 필요)" 안내
- 재색인은 변경마다 하지 않고 문서 관리 창을 닫을 때 한 번만 실행(채팅창 안내 반복 방지)
- 한계: 빈 섹션은 문서 형식상 저장되지 않음 → 새 섹션은 Q&A를 1개 이상 넣고 저장해야 기록됨(패널·상태줄에 안내)
- 주의: 즉시 저장은 그때까지 수정한 Q&A 내용도 함께 저장함
- 확인(로컬 사본): 이름 변경 즉시 저장, 연속 변경 순차 저장, 빈 섹션 추가·삭제 시 저장 안 함,
  빈 섹션 삭제로 번호가 당겨진 섹션 저장, 401 안내, 닫을 때 재색인 1회, 저장 및 재색인 버튼 정상

### 문제: 추가한 섹션이 저장되지 않음 → 해결
- 원인: 운영 서버 파서가 Q&A 없는 섹션 제목을 버림(`/api/parse-docx`로 확인: 빈 `Ⅱ.` 사라짐)
- 해결: 빈 섹션은 저장 시 숨김 자리표시 항목 1개(`(빈 섹션 — Q&A 없음)` / `[EMPTY_SECTION]`)를 넣어 보냄
  - 운영 서버 파서가 이 방식으로 섹션을 유지하는 것 확인(읽기 전용 파싱 API)
  - 화면(문서 관리)과 챗봇 검색에서는 자리표시를 숨김, 실제 Q&A가 생기면 자동으로 빠짐
  - 이제 섹션 추가·수정·삭제 모두 즉시 저장
- 부작용: Word 파일에는 빈 섹션마다 "(빈 섹션 — Q&A 없음)" 항목이 보임, 서버 Q 번호가 그만큼 하나씩 밀림
- 확인(로컬 사본): 추가→다시 열어도 유지, 챗봇 청크에 자리표시 없음, 빈 섹션 이름 변경 유지,
  Q&A 추가 시 자리표시 제거, 빈 섹션 삭제 후 사라짐

### 최종 점검 (운영 서버 적용 전)
- 보안: `escHtml`이 따옴표를 이스케이프하지 않아, 공유 문서의 섹션명·등록자가 속성값에 들어갈 때 스크립트 주입 가능 → 따옴표까지 이스케이프
  (따옴표가 든 이름으로 화면을 그려 주입된 속성 0개 확인). 챗봇 참고 구간의 섹션명도 이제 이스케이프됨
- 서버 주소: `:3002`(로컬 정적 서버)나 파일로 열 때만 운영 주소 사용, 그 외에는 같은 오리진 → 운영 서버가 80/443·프록시로 서빙해도 동작
- 저장 및 재색인이 섹션 즉시 저장과 겹치지 않게 대기
- 문법 검사(backend.py, index.html 스크립트), 운영 서버 연결·자료 로딩·실제 질문 응답 확인

### 운영 서버 적용 방법 (중요)
- `index.html`: 운영 서버의 파일을 이 버전으로 교체
- `backend.py`: **저장소 버전으로 통째로 덮어쓰지 말 것.** 운영 서버 버전에는 저장소에 없는 기능이 있음
  (`GET /`에서 index.html 서빙, 저장 시 로그인 요구로 추정). 아래 두 군데만 운영 파일에 직접 반영
  1. `_parse_qna_paragraphs`의 섹션 정규식 `^[ⅠⅡⅢⅣⅤⅥⅦⅧⅨⅩ]` → `^[ⅠⅡⅢⅣⅤⅥⅦⅧⅨⅩⅬⅭ]` (50~89번 섹션)
  2. `save_qna`에서 `SECTION_ORDER` 정렬 2줄 삭제 → 받은 순서대로 저장
- 적용 후 `http://112.160.143.66:8000/`로 접속해 문서 관리(섹션 추가·수정·삭제, 등록자) 확인

## 검증
로컬 백엔드 + 로컬 docx 사본으로 저장 왕복 테스트(브라우저 요청을 로컬로 돌려서 운영 서버에는 저장하지 않음):
- 1~99 번호 모두 고유, 100번째 차단
- 섹션 이름 변경 시 소속 항목 3개 함께 이동, 항목 있는 섹션 삭제 차단
- 빈 섹션(Ⅷ) 삭제 → 뒤 번호 자동 재부여(Ⅰ부터 연속)
- 11·41·51·91·99번째 섹션에 항목 추가 → 저장 → 다시 불러와 모두 유지(`Ⅼ` 포함), 등록자 복원
- 섹션 쪼개짐 없음, 챗봇 청크 28개 중 `[BY:]` 노출 0
- 테스트 후 로컬 docx는 백업본으로 원상복구
- 운영 서버는 읽기만 확인(섹션 7개, 항목 22개, 섹션 버튼 정상)

## 이슈 및 해결
- 저장 시 서버의 고정 목록 정렬을 없애면 새 항목이 섹션을 쪼개는 문제 → 화면에서 섹션 순서로 묶어 보내도록 수정
- 빈 섹션이 저장되지 않아 다시 열면 번호 빈칸 → 다음 번호를 "안 쓰는 번호"로 선택

## 차후작업 (운영 서버 112.160.143.66, 서버 관리자 반영 필요)
운영 서버 backend.py에 아래 두 가지가 없으면:
1. 섹션 인식 정규식 `^[ⅠⅡⅢⅣⅤⅥⅦⅧⅨⅩ]` → `^[ⅠⅡⅢⅣⅤⅥⅦⅧⅨⅩⅬⅭ]`
   - 없으면 50~89번 섹션(Ⅼ로 시작)이 저장 후 앞 섹션에 합쳐짐 (1~49, 90~99번은 지금도 정상)
2. `save_qna`에서 `SECTION_ORDER` 기준 정렬 제거, 받은 순서대로 저장
   - 운영 서버가 고정 목록으로 정렬한다면, 이름을 바꾼 기본 섹션이 저장 후 맨 뒤로 밀릴 수 있음
   - 운영 서버의 정렬 방식은 저장에 로그인이 필요해 확인하지 못함
